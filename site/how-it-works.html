The whole

The specification in SpecTec

SpecTec (spec/spectec/, {{spectec_total_files}} files) is the human-readable formal representation of ECMA-262 in this repository. Instead of bolting an ad-hoc HTML overlay onto generated Lean syntax trees, the specification is expressed directly in SpecTec's typed declarations:

  • Declarations (00-decls.spectec): Every specification clause (clause @sec-…, including named phrase helpers @ph-…), internal slot and Record field (field [[…]]), specification constant (enum ~…~), Record and object sort hierarchy (syntax Name defined { super […] record … }), internal method signature (method [[…]]), syntax-directed operation (sdo Name), and editorial notation primitive (extern def $Prim).
  • Grammars and early errors (01..08-*.spectec): All six ECMA-262 grammars — numeric string, lexical, syntactic, RegExp, Annex B and JSON — written as grammar <kind> and rule <kind> |Nonterminal|[Params] :: { | … } with parameter guards ([+Await], [~Yield]), but not exclusions, [lookahead …] restrictions and [no LineTerminator here], followed by early_error rules, 09-tables.spectec, and the intrinsic realm definition in 10-realm.spectec.
  • Clause algorithms (clauses/*.spectec, {{spectec_clause_files}} modules): Every abstract operation (kind ao), built-in function (kind builtin), syntax-directed row (kind sdo) and internal method (kind method) as a typed def @sec-… "Name" (kind … params […] -> …) vars […] { … } block ({{spectec_defs}} definitions in all). Steps use structured control flow (let, set, if / else_if / else, repeat_while, for_each, perform, return, throw, assert), explicit ? and ! completion unwrapping, type tests (is ty {Object}, is val {~empty~}), slot accesses (x[[Slot]]), and calls to @sec-… clauses or $Prim primitives.

Bidirectional bijections: spec.html ↔ SpecTec ↔ Lean

The specification's source, spec.html, is pinned at a revision of tc39/ecma262 (with any active proposals from spec/proposals.txt merged by scripts/spec_text.py{{proposal_link}}). Three automated round-trips keep spec.html, SpecTec, and the downstream Lean representation locked together:

  1. spec.html ↔ SpecTec (crates/spectec-html, scripts/html_bijection.py): Using four small presentation tables in spec/html/ (English call templates, grammar attributes, clause headers, and step patches), spectec-html renders every SpecTec grammar block, algorithm, equation and early-error rule back into ecmarkup HTML and splices them into spec.html with zero byte diffs.
  2. SpecTec ↔ SpecTec (spectec roundtrip): Every .spectec file — structured and prose alike — is parsed into SpecTec's AST and pretty-printed back byte for byte.
  3. SpecTec ↔ Lean (spectec emit & ecma-print, scripts/bijection.py): crates/spectec compiles spec/spectec/ into gitignored Lean modules, and the Lean printer ecma-print prints all {{spectec_struct_files}} structured .spectec files back from those compiled definitions byte for byte.

Symbolic names and sorted declarations

In SpecTec, everything is written by name (@sec-iscallable, [[Call]], ~start+end~, |IdentifierName|). When crates/spectec emits Lean code for the machine and proofs, it collects all declared and referenced names across each namespace in spec/spectec/, sorts them lexicographically (0..N-1), and generates symbolic constants in Ecma.Known. Because downstream Lean code references symbolic names rather than raw numbers, editing a clause or applying a proposal stays local to the changed SpecTec definitions.

Prose concepts in SpecTec: syntax, relation and laws

Algorithms and grammars are only half of ECMA-262: §5.1, §6, §9, §21 and §29 state in English prose what values are, how grammars derive parse trees, how shared memory behaves, and what a host environment may do. Those prose sections are formalized in {{spectec_prose_files}} SpecTec modules under spec/spectec/prose/ ({{spectec_prose_lines}} lines) using four declarations:

  • syntax (abstract sorts, records and variants): Ecma.Model declares the abstract carriers and operations of every specification sort (mathematical values, IEEE 754 binary64 Numbers, BigInts, UTF-16 Strings, Symbols, Parse Nodes, Lists, Data Blocks, CharSets, Records, property tables and the store) without fixing any implementation; Val, Cell and Host define runtime values, store cells and the host interface over any Model.
  • relation (inductive inference rules): Declarative specifications such as §5.1 grammar derivations (Grammar.Derives), the correspondence between abstract Parse Nodes and derivation trees (Model.NodeRel), and §29 candidate-execution orders (MemoryModel.HB) are written as Horn-style inference rules (rule name : Conclusion :- Premise1, Premise2;).
  • laws (axiomatic requirements quoting spec.html): Model.Laws and its companion blocks ({{all_model_laws}} laws: {{model_laws}} core, {{num_laws}} for Numbers, {{byte_laws}} for Data Blocks, {{unicode_laws}} for Unicode, and {{parent_laws}} for Parse Node parents), Model.ParseLaws / Model.CoverLaws / Model.NodeLaws ({{parse_laws}} laws for parsing, covers and Parse Nodes), MemoryModel.ValidWith ({{memory_laws}} laws for §29 candidate executions and shared reads), and Host.WF ({{host_laws}} laws across {{host_topics}} topics, constraining host hooks and choices over the host-call log) state what any conforming model, parser and host must satisfy. Every law begins with a --- sec-id: docstring quoting the governing sentence of spec.html and giving a one-line Reading:, checked against spec.html by scripts/law_quotes.py (see timeoutAfter).
  • def (pure specification helpers): Total helper functions over Model and State used to state relations and laws cleanly, with no tactics, proofs or partial recursion.

Specification decisions and errata

Where ECMA-262 as written is contradictory, incomplete, or disagrees with every engine and test262, SpecTec resolves the ambiguity directly in spec/spectec/ rather than carrying a runtime .emu overlay or command-line errata switches. Every such choice is documented in spec/DECISIONS.md, including {{errata}} active specification errata and proposed normative changes ({{errata_defects}} defects of the text and {{errata_proposals}} proposed normative {{errata_proposals_noun}}): {{errata_test262}} bake in the reading test262 requires, {{errata_proposed}} bake in a proposed fix, and {{errata_literal}} keep the literal wording so that reaching a broken Assert: stops at the exact offending step.{{errata_sentence}}

Downstream: the small-step machine and proved engine

Everything under lean/ consumes the compiled SpecTec specification:

  • Specification semantics (lean/Ecma): lean/Ecma/Lower expands editorial macros such as IfAbruptRejectPromise and linearizes SpecTec algorithm bodies while preserving step paths; Ecma.Machine.step defines one small-step transition over call frames for any Model and Host (Machine.Runs); and Ecma.Implements states what it means for an implementation to conform. lean/Ecma contains zero theorems, tactics, partial defs or unsafe code (scripts/quick_check.py).
  • Reference engine and proofs (lean/Engine): Concrete carriers (exact rationals, IEEE 754 binary64, UTF-16 arrays, a chunked store), a proved parser over all six SpecTec grammars (Engine.Claims.parseLaws, Engine.Claims.coverLaws, Engine.Claims.nodeLaws), a concrete host with jobs, agents, modules and $262, and verified fast-path shortcuts ({{engine_lines}} lines of implementation, {{proof_lines}} lines of proofs). It runs JavaScript programs and {{t262_link}} as {{RUN}}, and What is proved explains Engine.implements and Engine.run_sound.
  • Interactive step debugger (lean/Debugger): Drives the specification machine step by step as {{DBG}} ({{debugger_lines}} lines, native and 64-bit WebAssembly), pausing on clauses, step paths, throws and Assert: stops.

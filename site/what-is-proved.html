The definition: Ecma.Implements

An implementation (Implementation) provides concrete values (a Model), a Host, host algorithms beside the specification's, and its own transition between machine configurations. Its transition may execute many specification steps at once or compute a fast-path shortcut directly. It implements the specification when three conditions hold:

{{implements_struct}}
model

Its values obey all {{all_model_laws}} SpecTec model laws: Model.Laws ({{model_laws}} core laws, joined with Model.NumLaws's {{num_laws}} for Numbers and Model.ByteLaws's {{byte_laws}} for Data Blocks), the Unicode laws (Model.UnicodeLaws, {{unicode_laws}}), and the Parse Node parent laws (Model.ParentLaws, {{parent_laws}}).

host

Its host obeys every SpecTec law the specification requires of a host (Host.WF, {{host_laws}} laws across {{host_topics}} topics).

step

Whether Asserts are checked or unchecked (chk): from any configuration the specification's machine reaches (Reached), a transition the implementation takes is zero or more transitions of the specification's machine; where the implementation finishes, the specification's machine finishes from there with the same result; or the implementation stops at a resource limit of its own (.stop .implLimit). It never answers otherwise than the specification.

The theorems, verbatim

The engine as an implementation, Engine.implementation o cells mc accel, bundles the concrete model Impl, its host under the options o over the cells cells, the host's own algorithms, and its transition with the store ceiling mc, with or without shortcuts (accel). Both theorems are in lean/Engine/Proofs/Model.lean and have no hypothesis beyond what they state.

The engine implements the specification

{{stmt:implements}}

For every option set of the host, every allocation of its cells, every store ceiling, with or without the shortcuts, the engine is an implementation of the specification in the sense above.

Every run of the engine is the specification's

{{stmt:run_sound}}

If the engine's run loop (runT), started on a call in a state with no suspended execution context, returns a result f, then the specification's machine, running the compiled SpecTec program with the engine's host, has a run from the same configuration that ends with f; or f is a stop at an implementation limit. A companion, Engine.run_sound_reached, proves the same from any configuration the specification's machine reaches, covering jobs and runs after preludes.

The parser and cover laws, sound and complete

{{stmt:parseLaws}} {{stmt:coverLaws}}

In lean/Engine/Claims.lean (proved in lean/Engine/Proofs/Parse/Laws.lean and Cover.lean): for every parser context and strictness flag, Model.parse is both sound and complete against GrammarCtx.ParseIs / GrammarCtx.Parses (Model.ParseLaws), and Model.cover is sound against GrammarCtx.CoverIs (Model.CoverLaws), alongside Engine.Claims.nodeLaws and Engine.Claims.parentLaws.

Proved, trusted, owed, outside

Proved What the theorems establish

  • The engine's values obey the SpecTec model laws and Unicode laws (Engine.Impl.laws, Engine.Impl.unicodeLaws).
  • The engine's host obeys all {{host_laws}} SpecTec host laws under every option set (Engine.SpecHost.wfBy).
  • The code table the engine runs equals the compiled SpecTec program plus the host's own algorithms where the specification defines none (Engine.P'_eq).
  • Each transition of the engine, shortcuts included, matches the specification's at every reachable configuration, with 0 native_decide pins; the {{runtime_pins}} checks on the generated program and parser tables are verified at run time (Engine.Machine.pinsOk; if any failed, Engine.setupAt falls back to Engine.Machine.plain).
  • The parser's soundness and completeness laws (Engine.Claims.parseLaws), the cover soundness law (Engine.Claims.coverLaws), and the laws of a Parse Node's parent (Engine.Claims.parentLaws) and of its children and descendants (Engine.Claims.nodeLaws), over Engine.Model.codePrims.
  • The set-ups covered: {{RUN}} by default and with --no-accel, under every --checked, --max-heap, every host option (--host-seed, --web-browser, --annex-b, --can-block, --resize-in-place), and with tracing, --sites and --cover.

Trusted Relied on, not proved

  • Lean's {{axiom_count}} standard axioms ({{axioms}}), crates/spectec's emitter, and Lean's kernel and compiler.
  • The implemented_by overrides: the run loop's observers (traceOut, noteOut, noteStep, the identity to the logic), and the model's binary64 operations addHw, mulHw, divHw, and Parent's treeIndex, treeHeight, parentFast.
  • The driver between runs: realm initialization, preludes and the main program as separate runs, snapshots and --serve's caches. None of them mutates suspended execution contexts, so each run starts from a configuration Reached covers. That is inspected in the code, not proved.

Owed Stated, not proved

  • None: every SpecTec law stated of the model, the host, and the parser (Model.ParseLaws, Model.CoverLaws, Model.NodeLaws) is proved of the engine.

Outside Not covered by the claim

  • The step debugger's loop (Debugger.Machine.runW, a partial definition): {{DBG}} steps the same machine, but its interactive loop is not proved.
  • Optional mark-and-sweep store collection ({{RUN}} --gc via Engine.GC.runGC, a partial loop, and {{DBG}}'s "gc" request): reclaiming unreachable cells in Engine.Model.ChunkedHeap while keeping live addresses monotonic is outside Engine.implements; default {{RUN}} runs without --gc.
  • Test results: the theorem says nothing about which {{t262_link}} tests pass.

What the theorem does not say

  1. That SpecTec is the English. The correspondence between spec/spectec/ and spec.html is enforced by mechanical checks rather than a mathematical theorem: crates/spectec-html splices all SpecTec grammars, algorithms, equations and early errors back into spec.html with zero byte diffs (scripts/html_bijection.py), spectec roundtrip and ecma-print (scripts/bijection.py) verify the SpecTec ↔ Lean round-trips byte for byte, and scripts/law_quotes.py verifies every law's quotation against spec.html. The resolved decisions in spec/DECISIONS.md and the SpecTec readings of prose laws are reviewed by humans.
  2. That every program gets an answer. The theorem governs runs that return from the engine's loop. A run may also stop at an implementation limit (the store ceiling or an exact power exceeding 230 bits), which the claim explicitly permits. Non-terminating runs produce no final value to compare.
  3. That every source text is decided within fixed limits. The parser's soundness and completeness laws (Engine.Claims.parseLaws, Engine.Claims.coverLaws) are proved where Model.parse decides, while fuel or nesting-depth limits leave the parse undecided (.stop .implLimit).
  4. That every host law matches its sentence word for word. Two host laws read their sentence more strictly than written (candidates for proposed normative changes) and two read theirs more weakly: see the host's laws.

The engine as an implementation

From lean/Engine/Claims.lean: the host's algorithms (hostAlgs: built-in functions, agent API hooks, HostLoadImportedModule, and entry-point drivers), none at an ID the specification defines; the host under options o; and the transition Engine.Machine.stepE: a stop at the store ceiling, else a verified shortcut where one applies (disabled when accel is false or if Engine.Machine.pinsOkThunk were false), else the specification's own step.

51. A maximum BigInt size: 2n ** (2n ** 40n) has an exact result in the text, which allows no maximum size

Location
§6.1.6.2 The BigInt Type (#sec-ecmascript-language-types-bigint-type), its first paragraph; §6.1.6.2.3 BigInt::exponentiate (#sec-numeric-types-bigint-exponentiate), step 3; §6.1.6.2.4 BigInt::multiply (#sec-numeric-types-bigint-multiply), step 1, and its note; §6.1.6.2.7 BigInt::add (#sec-numeric-types-bigint-add), step 1; §6.1.6.2.8 BigInt::subtract (#sec-numeric-types-bigint-subtract), step 1; §6.1.6.2.9 BigInt::leftShift (#sec-numeric-types-bigint-leftShift), step 2; §21.2.2.2 BigInt.asUintN (#sec-bigint.asuintn), step 3.
Kind
proposed normative change (not a defect: the text is consistent and gives every result).
Model erratum
BigIntMaximumSize, baked-in SpecTec reading proposed ($BigIntTooLarge in spec/spectec/clauses/S06.spectec and S21.spectec); its readings: literal, proposed. The proposed reading asks the host before the result is formed whether it would exceed the implementation's maximum (the model's host answers true past 230 bits, covering exponentiate, leftShift, multiply, add, subtract, and asUintN) and throws a RangeError if so; the literal reading forms the result whatever its size.
Upstream
Checked 2026-11-19: none found that proposes this (searched for BigInt with "maximum size" and with "size limit"). Related: issue #1391 (open, 2019-01), "Extending defining out-of-memory beyond ArrayBuffer", asks whether BigInt will have a defined out-of-memory error as ArrayBuffer has; issue #4063 (closed, 2026-10, as not planned), "Specify that exceeding resource limits may throw", asked it of resource limits in general.

Text

§6.1.6.2:

The BigInt type represents an integer value. The value may be any size and is not limited to a particular bit-width.

BigInt::exponentiate:

1. If exponent < 0ℤ, throw a RangeError exception.

2. If base = 0ℤ and exponent = 0ℤ, return 1ℤ.

3. Return base raised to the power exponent.

BigInt::multiply, with its note:

1. Return x × y.

Even if the result has a much larger bit width than the input, the exact mathematical answer is given.

BigInt::leftShift:

1. If y < 0ℤ, then

a. Return ℤ(floor(ℝ(x) / 2-ℝ(y))).

2. Return x × 2ℤy.

Problem

The three operations are the ones whose result can be far larger than their operands, and each returns its exact result, of any size. An implementation can hold BigInts only up to some size. Read as written, 2n ** (2n ** 40n) is 2240, a BigInt of 240 + 1 bits (about 137 GB), and a conforming implementation must produce it; one that throws a RangeError there departs from the text: a search of spec.html found no sentence that sets or allows a limit on the size of a BigInt.

The proposal is to say what an implementation with a limit does. In each of the three, before its result is formed, the proposed step:

If the result would exceed the implementation's maximum BigInt size, throw a RangeError exception.

The maximum stays implementation-defined. The change is normative: it makes a RangeError a conforming result where the text now requires the exact BigInt.

The proposed wording below does not settle every consequence. BigInt::multiply, BigInt::add, BigInt::subtract, and BigInt::leftShift return "a BigInt" and would return a completion record (their headers and their rows in §6.1.6's Numeric Type Operations table); ApplyStringOrNumericBinaryOperator (§13.15.3) calls them in its last step, "Return operation(leftNumber, rightNumber)", which would take ?; BigInt::signedRightShift calls BigInt::leftShift(x, -y), which shifts left when y is negative (2n >> -(2n ** 40n)) and therefore also takes ?, as do the four UpdateExpression (++/--) evaluation rules calling BigInt::add and BigInt::subtract; and the note of BigInt::multiply would end "unless it exceeds the implementation's maximum BigInt size". Under BigIntMaximumSize, BigInt.asUintN, BigInt::add, and BigInt::subtract are covered alongside exponentiate, leftShift, and multiply.

Examples

No example program is in examples/ for this proposal, and no engine's output is recorded in RESULTS.md for it.

try { print((2n ** (2n ** 40n)) > 0n); } catch (e) { print("**: " + e.constructor.name); }
try { print((1n << (2n ** 40n)) > 0n); } catch (e) { print("<<: " + e.constructor.name); }
var big = 1n << (2n ** 29n);
try { print((big * big * big) > 0n); } catch (e) { print("*: " + e.constructor.name); }
** << *
literal text true (an exact result of 240 + 1 bits) true (likewise) true (about 3 × 229 bits)
proposed text RangeError where the result exceeds the implementation's maximum likewise likewise
formal model, proposed reading (the default) **: RangeError <<: RangeError *: RangeError

The model was not run under its literal reading here: it would have to form a BigInt of 240 + 1 bits. The model's tests tests/run/bigint_huge_power.js (3n ** (1n << 40n)) and tests/run/bigint_huge_left_shift.js (2n << (1n << 64n)) end throw: RangeError under the default reading, and tests/run/bigint_power_below_limit.js computes 3n ** 5592406n (8863754 bits), below the model's limit.

40. Annex B: what §B.1.2's ordered alternatives choose, and which |Pattern| its group-number condition counts

Location
§B.1.2 Regular Expressions Patterns (#sec-regular-expressions-patterns), its first paragraph and AtomEscape's second alternative, with its note; §22.2.1.2 CountLeftCapturingParensWithin (#sec-countleftcapturingparenswithin) and §B.1.2.2 CountLeftCapturingParensWithin and CountLeftCapturingParensBefore (#sec-countleftcapturingparens-annexb).
Kind
ambiguity (the ordering sentence); self-reference (the condition).
Model erratum
AnnexBRegExpOrder and AnnexBGroupCount, default reading test262 for both; the readings of each: literal, test262, proposed. The test262 and proposed readings read the ordering as commitment for the nonterminals §B.1.2 gives, and take the count from a parse with the condition taken as true: the proposed wording below. Under the literal reading the run stops on a pattern with more than one parse.
Upstream
Checked 2026-11-19: PR #2445 (open, 2021-06), "Editorial: Eliminate order-disambiguation from Annex B Pattern-grammar", replaces the ordering sentence by lookahead restrictions; its ConstrainedDecimalEscape keeps the condition's "the |Pattern| containing |DecimalEscape|"; it is not merged. PR #2228 (merged 2020-12, commit 67dc0c208), "Editorial: Swap 2 alternatives of Term in Annex B", swapped Term's alternatives because, under the ordering sentence, Atom matches wherever Atom Quantifier would.

Text

The first paragraph of §B.1.2 (its "…" is a cross-reference to §22.2.1 Patterns):

The syntax of … is modified and extended as follows. These changes introduce ambiguities that are broken by the ordering of grammar productions and by contextual information. When parsing using the following grammar, each alternative is considered only if previous production alternatives do not match.

AtomEscape[UnicodeMode, NamedCaptureGroups] :: [+UnicodeMode] DecimalEscape [~UnicodeMode] DecimalEscape [> but only if the CapturingGroupNumber of DecimalEscape is ≤ CountLeftCapturingParensWithin(the Pattern containing DecimalEscape)]

…

and the note after the grammar (the guard elided is [~UnicodeMode]):

When the same left-hand sides occurs with both [+UnicodeMode] and … guards it is to control the disambiguation priority.

Problem

The grammar needs an order: /a{1}/ is one Term (a quantified) or four (a, {, 1, }), \b is an Assertion or an identity escape, \1 a DecimalEscape or a LegacyOctalEscapeSequence. §5.1 defines a grammar's language and parse trees declaratively; the sentence is procedural, and says neither what an alternative "matches" nor how nested choices combine. Three readings:

  • Commitment for every nonterminal, as in a parsing expression grammar: no pattern with a Term parses, since §22.2.1's Alternative :: [empty] | Alternative Term always takes [empty]. But Alternative and Disjunction are §22.2.1's, not "the following grammar".
  • Commitment for the nonterminals §B.1.2 gives: a node uses an alternative only if no earlier alternative of its nonterminal derives any span from where it starts. It is well defined and gives the engines' answers: \b is an Assertion wherever it occurs, so /\b*/ has nothing to repeat.
  • A priority among complete parses (a later alternative is used only where no earlier one leads to a parse of the whole pattern): also well defined, but it accepts /\b*/, /\B+/ and /a\b?/, whose only complete parse quantifies b read as an identity escape.

The condition reads "the |Pattern| containing |DecimalEscape|", the tree being chosen, and whether \N is a DecimalEscape is part of that choice: it is evaluated on the tree it selects. For /\1(a)/ the Pattern has one capturing group however \1 is read, so only the backreference is consistent; but the text gives no rule for finding the tree, and a pattern whose count depended on the choice could have no consistent parse or two. It does not: the alternatives the condition decides between derive only digits, never a (. So the count can be taken from the parse with the condition true.

test262

annexB/built-ins/RegExp and annexB/language/literals/regexp test these choices (legacy-octal-escape.js for \1, RegExp-decimal-escape-not-capturing.js for \2 with one group, extended-pattern-char.js, identity-escape.js, quantifiable-assertion-followed-by.js); they pass under both commitment for B.1.2's nonterminals and priority among complete parses. None tests /\b*/ or /a\b?/ under Annex B, where the two readings differ.

The program

The example is a Script. Its runs on the engines and on the model: the examples' runs.

Source examples/40-annexb-regexp-order-group-count.js
// §B.1.2: "each alternative is considered only if previous production alternatives do not match", and
// AtomEscape's DecimalEscape "only if the CapturingGroupNumber of DecimalEscape is ≤
// CountLeftCapturingParensWithin(the Pattern containing DecimalEscape)". Each pattern is compiled with no
// flags; the string is matched against it.
if (typeof print === "undefined") globalThis.print = console.log;
var cases = [["a{1}", "a"], ["\\b*", ""], ["a\\b?", "ab"], ["\\x4", "x4"], ["{,1}", "{,1}"], ["[\\b]", "\b"],
             ["\\c1", "\\c1"], ["\\1(a)", "a"], ["\\2(a)(b)", "ab"], ["\\3(a)(b)", "\x03ab"], ["(a)\\10", "a\x08"],
             ["\\1", "\x01"]];
for (var [p, s] of cases) {
  var r;
  try { r = String(new RegExp(p).test(s)); } catch (e) { r = e.constructor.name; }
  print(JSON.stringify(p) + " on " + JSON.stringify(s) + ": " + r);
}

03. A built-in async function's promise fulfils with undefined

Location
§10.3.3 BuiltinCallOrConstruct (#sec-builtincallorconstruct), step 10.b.iii, with §27.10.5.2 AsyncBlockStart (#sec-asyncblockstart), steps 1.f–1.g.
Kind
contradiction (the literal result is not what the algorithm of an async built-in returns).
Model erratum
BuiltinReturnCompletion, default reading test262; its readings: literal, test262, proposed. The test262 and proposed readings are the same: step 10.b.iii turns a normal completion into a return completion (Proposed wording).
Upstream
Checked 2026-11-19: PR #4074 (open, 2026-11), "Normative: Fix async built-in functions resolving to undefined", reports this (with Array.fromAsync([1, 2, 3])) and proposes a fix; no issue was found (searched for "BuiltinCallOrConstruct"). Step 10, the built-in async path, came with PR #2942 (merged 2025-12, commit 7029ed1b2).
On this site
BuiltinReturnCompletion on Spec issues & errata (defect of the text; SpecTec bakes in the test262 reading)

Text

BuiltinCallOrConstruct, for func.[[Async]] true:

b. Let resultsClosure be a new Abstract Closure with no parameters that captures … and performs the following steps when called:

i. Let result be the Completion Record that is the result of evaluating func …

iii. Return Completion(result).

c. Perform AsyncFunctionStart(promiseCapability, resultsClosure).

AsyncBlockStart:

f. If result is a normal completion, then

i. Perform ! Call(promiseCapability.[[Resolve]], undefined, « undefined »).

g. Else if result is a return completion, then

i. Perform ! Call(promiseCapability.[[Resolve]], undefined, « result.[[Value]] »).

and §5.2.4.4 Implicit Normal Completion: in a built-in function, "Return v" returns NormalCompletion(v).

Problem

Array.fromAsync ends with "Return A" (§23.1.2.2, steps 3.j.ii.10.b and 3.k.ix of its async closure), a normal completion. Step 10.b.iii returns it unchanged, AsyncBlockStart receives a normal completion, and step 1.f resolves the promise with undefined. So every built-in async function's promise fulfils with undefined, whatever its algorithm returns. For an ECMAScript async function, return v evaluates to a return completion, which is why step 1.g exists; the built-in path has nothing that makes one.

The specification's two built-in async functions are Array.fromAsync and AsyncDisposableStack.prototype.disposeAsync. disposeAsync returns undefined, so only Array.fromAsync shows the defect, on every call.

Examples

examples/03-builtin-async-return-value.js (outputs: the recorded runs):

Array.fromAsync([1, 2]).then(function (v) {
  print("fromAsync fulfils with " + JSON.stringify(v));
});
output
literal text fromAsync fulfils with undefined
V8, SpiderMonkey, JavaScriptCore fromAsync fulfils with [1,2]
formal model, literal reading fromAsync fulfils with undefined
formal model, test262 reading (default) and proposed reading fromAsync fulfils with [1,2]

test262

The Array.fromAsync tests that read the fulfilment value require the array, e.g. built-ins/Array/fromAsync/asyncitems-array-add.js and built-ins/Array/fromAsync/asyncitems-arraylike-holes.js (each awaits the promise and compares the result with assert.compareArray). They fail under the literal text.

The program

The example is a Script. Its runs on the engines and on the model: the examples' runs.

// BuiltinCallOrConstruct 10.b.iii and AsyncBlockStart 1.f: the fulfilment
// value of a built-in async function. Literal text: undefined.
if (typeof print === "undefined") globalThis.print = console.log;
Array.fromAsync([1, 2]).then(function (v) {
  print("fromAsync fulfils with " + JSON.stringify(v));
});

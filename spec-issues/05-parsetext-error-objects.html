05. ParseText creates SyntaxError objects without a realm

Location
§11.1.6 Static Semantics: ParseText (#sec-parsetext), step 5; §22.2.3.4 Static Semantics: ParsePattern (#sec-parsepattern), step 1.a, and its §B.1.2.9 version (#sec-parsepattern-annexb).
Kind
missing context and undefined sort (error).
Model erratum
ParseTextErrorObjects, baked-in SpecTec reading proposed (spec/spectec/clauses/Helpers.spectec, @formal-parsetextin, @ph-syntax-errors, @sort-error; lean/Ecma/Lower/LinEarly.lean, newSyntaxError). Rather than following the literal text (which leaves the Realm Record unspecified when creating SyntaxError objects and tests an undefined sort error in ten caller steps), SpecTec bakes in three choices: (1) @formal-parsetextin, ParsePattern and early-error rules allocate a singleton SyntaxError object in currentRealm; (2) the test host (lean/Engine/Host/Opts.lean) pushes an execution context for the target realm before top-level ParseScript and ParseModule so currentRealm is defined on an otherwise empty stack; and (3) @sort-error defines "error" as an Object with an [[ErrorData]] internal slot (tc39/ecma262#3868) so ToNumber("x"), BigInt("x") and other ParseText callers do not stop on an undefined sort.
Upstream
Checked 2026-11-19: none found that reports it (searched for "ParseText" with realm and with SyntaxError). Issue #3868 (open, 2026-05), "How should ParseText results be consumed?", asks how callers test the result, not where its objects are created; issue #1462 (open, 2019-03), "Current Realm record when creating new objects in [[Construct]]", asks the same realm question of the objects [[Construct]] creates. ParseText's NOTE, now step 3, came with PR #3956 (merged 2026-10, commit 21e4774e4).
On this site
ParseTextErrorObjects on Spec issues & errata (defect of the text; SpecTec bakes in the proposed reading)

Text

5. Return a List of one or more SyntaxError objects representing the parsing errors and/or early errors. If more than one parsing error or early error is present, the number and ordering of error objects in the list is implementation-defined, but at least one must be present.

ParsePattern:

1. If v is true and u is true, then

a. Let parseResult be a List containing one or more SyntaxError objects.

Problem

ParseText is a static semantics, but creating an object changes an agent's state, and a SyntaxError object belongs to a realm: its [[Prototype]] is some realm's %SyntaxError.prototype%. The text says neither which realm nor when the objects come into existence. A host may call ParseScript or ParseModule while no execution context is running, when there is no current Realm Record. ParseScript and ParseModule have a realm parameter, but ParseText is not given it.

ParseText also runs inside ordinary operations: StringToNumber (Number("x")), StringToBigInt, ParseHexOctet (decodeURI), IsTimeZoneOffsetString, and, by ParsePattern, IsValidRegularExpressionLiteral. Read literally, each failed parse there creates objects that nothing uses. No algorithm of the specification reads an object from the List: PerformEval, CreateDynamicFunction and RegExpInitialize throw a new SyntaxError of their own, Decode throws a URIError, and StringToNumber, StringToBigInt, IsTimeZoneOffsetString and IsValidRegularExpressionLiteral return NaN, undefined or false. (parseFloat, ParseJSON and ParseTimeZoneOffsetString assert that their parse succeeds.) Only ParseScript and ParseModule pass the List out, to the host, and the host needs objects there: HTML's "create a classic script" and "create a JavaScript module script" store the List's first element as the script's parse error and rethrow it.

So the objects matter only at ParseScript and ParseModule, which know their realm. The proposed change: ParseText and ParsePattern return errors, and those two operations create the objects in realm.

Examples

examples/05-parsetext-error-objects.js (outputs: the recorded runs) shows the errors that are observable, each caller's own SyntaxError from the current realm:

try { eval("var x = ;"); } catch (e) { print(e instanceof SyntaxError); }
try { Function("a", "return a +;"); } catch (e) { print(e instanceof SyntaxError); }
try { new RegExp("("); } catch (e) { print(e instanceof SyntaxError); }
output
literal text true, true, true
V8, SpiderMonkey, JavaScriptCore true, true, true
formal model (proposed reading baked into SpecTec) true, true, true

A host hook such as test262's $262.evalScript, which throws the List's first element (INTERPRETING.md), is where the objects' realm could show.

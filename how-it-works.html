ECMA-262 formalized in SpecTec, bijective with spec.html, compiled and proved in Lean

How it works

The specification lives in SpecTec (spec/spectec/) in two parts: structured SpecTec for ECMA-262's algorithms, grammars, early errors and tables (bijective with spec.html), and prose SpecTec modules for its abstract sorts, grammar and §29 memory relations, and the 246 model, parser, memory-model and host laws that quote the English text. Everything else — the Lean specification semantics, the proved reference engine, and the WebAssembly debugger — is downstream of SpecTec.

The whole

The specification in SpecTec

SpecTec (spec/spectec/, 62 files) is the human-readable formal representation of ECMA-262 in this repository. Instead of bolting an ad-hoc HTML overlay onto generated Lean syntax trees, the specification is expressed directly in SpecTec's typed declarations:

  • Declarations (00-decls.spectec): Every specification clause (clause @sec-…, including named phrase helpers @ph-…), internal slot and Record field (field [[…]]), specification constant (enum ~…~), Record and object sort hierarchy (syntax Name defined { super […] record … }), internal method signature (method [[…]]), syntax-directed operation (sdo Name), and editorial notation primitive (extern def $Prim).
  • Grammars and early errors (01..08-*.spectec): All six ECMA-262 grammars — numeric string, lexical, syntactic, RegExp, Annex B and JSON — written as grammar <kind> and rule <kind> |Nonterminal|[Params] :: { | … } with parameter guards ([+Await], [~Yield]), but not exclusions, [lookahead …] restrictions and [no LineTerminator here], followed by early_error rules, 09-tables.spectec, and the intrinsic realm definition in 10-realm.spectec.
  • Clause algorithms (clauses/*.spectec, 25 modules): Every abstract operation (kind ao), built-in function (kind builtin), syntax-directed row (kind sdo) and internal method (kind method) as a typed def @sec-… "Name" (kind … params […] -> …) vars […] { … } block (1,627 definitions in all). Steps use structured control flow (let, set, if / else_if / else, repeat_while, for_each, perform, return, throw, assert), explicit ? and ! completion unwrapping, type tests (is ty {Object}, is val {~empty~}), slot accesses (x[[Slot]]), and calls to @sec-… clauses or $Prim primitives.

Bidirectional bijections: spec.html ↔ SpecTec ↔ Lean

The specification's source, spec.html, is pinned at a revision of tc39/ecma262 (with any active proposals from spec/proposals.txt merged by scripts/spec_text.py (Applying a proposal shows one applied)). Three automated round-trips keep spec.html, SpecTec, and the downstream Lean representation locked together:

  1. spec.html ↔ SpecTec (crates/spectec-html, scripts/html_bijection.py): Using four small presentation tables in spec/html/ (English call templates, grammar attributes, clause headers, and step patches), spectec-html renders every SpecTec grammar block, algorithm, equation and early-error rule back into ecmarkup HTML and splices them into spec.html with zero byte diffs.
  2. SpecTec ↔ SpecTec (spectec roundtrip): Every .spectec file — structured and prose alike — is parsed into SpecTec's AST and pretty-printed back byte for byte.
  3. SpecTec ↔ Lean (spectec emit & ecma-print, scripts/bijection.py): crates/spectec compiles spec/spectec/ into gitignored Lean modules, and the Lean printer ecma-print prints all 36 structured .spectec files back from those compiled definitions byte for byte.

Symbolic names and sorted declarations

In SpecTec, everything is written by name (@sec-iscallable, [[Call]], ~start+end~, |IdentifierName|). When crates/spectec emits Lean code for the machine and proofs, it collects all declared and referenced names across each namespace in spec/spectec/, sorts them lexicographically (0..N-1), and generates symbolic constants in Ecma.Known. Because downstream Lean code references symbolic names rather than raw numbers, editing a clause or applying a proposal stays local to the changed SpecTec definitions.

Prose concepts in SpecTec: syntax, relation and laws

Algorithms and grammars are only half of ECMA-262: §5.1, §6, §9, §21 and §29 state in English prose what values are, how grammars derive parse trees, how shared memory behaves, and what a host environment may do. Those prose sections are formalized in 26 SpecTec modules under spec/spectec/prose/ (4,304 lines) using four declarations:

  • syntax (abstract sorts, records and variants): Ecma.Model declares the abstract carriers and operations of every specification sort (mathematical values, IEEE 754 binary64 Numbers, BigInts, UTF-16 Strings, Symbols, Parse Nodes, Lists, Data Blocks, CharSets, Records, property tables and the store) without fixing any implementation; Val, Cell and Host define runtime values, store cells and the host interface over any Model.
  • relation (inductive inference rules): Declarative specifications such as §5.1 grammar derivations (Grammar.Derives), the correspondence between abstract Parse Nodes and derivation trees (Model.NodeRel), and §29 candidate-execution orders (MemoryModel.HB) are written as Horn-style inference rules (rule name : Conclusion :- Premise1, Premise2;).
  • laws (axiomatic requirements quoting spec.html): Model.Laws and its companion blocks (148 laws: 116 core, 12 for Numbers, 9 for Data Blocks, 7 for Unicode, and 4 for Parse Node parents), Model.ParseLaws / Model.CoverLaws / Model.NodeLaws (7 laws for parsing, covers and Parse Nodes), MemoryModel.ValidWith (19 laws for §29 candidate executions and shared reads), and Host.WF (72 laws across 10 topics, constraining host hooks and choices over the host-call log) state what any conforming model, parser and host must satisfy. Every law begins with a --- sec-id: docstring quoting the governing sentence of spec.html and giving a one-line Reading:, checked against spec.html by scripts/law_quotes.py (see timeoutAfter).
  • def (pure specification helpers): Total helper functions over Model and State used to state relations and laws cleanly, with no tactics, proofs or partial recursion.

Specification decisions and errata

Where ECMA-262 as written is contradictory, incomplete, or disagrees with every engine and test262, SpecTec resolves the ambiguity directly in spec/spectec/ rather than carrying a runtime .emu overlay or command-line errata switches. Every such choice is documented in spec/DECISIONS.md, including 56 active specification errata and proposed normative changes (53 defects of the text and 3 proposed normative changes): 33 bake in the reading test262 requires, 13 bake in a proposed fix, and 10 keep the literal wording so that reaching a broken Assert: stops at the exact offending step. Spec issues & errata quotes each entry's sentences and alternative readings, tracks upstream issues and PRs, links to its long-form write-up, and verifies a demonstration program where one applies.

Downstream: the small-step machine and proved engine

Everything under lean/ consumes the compiled SpecTec specification:

  • Specification semantics (lean/Ecma): lean/Ecma/Lower expands editorial macros such as IfAbruptRejectPromise and linearizes SpecTec algorithm bodies while preserving step paths; Ecma.Machine.step defines one small-step transition over call frames for any Model and Host (Machine.Runs); and Ecma.Implements states what it means for an implementation to conform. lean/Ecma contains zero theorems, tactics, partial defs or unsafe code (scripts/quick_check.py).
  • Reference engine and proofs (lean/Engine): Concrete carriers (exact rationals, IEEE 754 binary64, UTF-16 arrays, a chunked store), a proved parser over all six SpecTec grammars (Engine.Claims.parseLaws, Engine.Claims.coverLaws, Engine.Claims.nodeLaws), a concrete host with jobs, agents, modules and $262, and verified fast-path shortcuts (12,291 lines of implementation, 57,206 lines of proofs). It runs JavaScript programs and test262 as ecma-run, and What is proved explains Engine.implements and Engine.run_sound.
  • Interactive step debugger (lean/Debugger): Drives the specification machine step by step as ecma-dbg (3,666 lines, native and 64-bit WebAssembly), pausing on clauses, step paths, throws and Assert: stops.

One clause, end to end

§7.2.3 IsCallable is three steps in spec.html:

§7.2.3 IsCallable ( arg )
  1. If arg is not an Object, return false.
  2. If arg has a [[Call]] internal method, return true.
  3. Return false.

In SpecTec. Clause §7.2.3 lives in spec/spectec/clauses/S07.spectec as a five-line def:

--- spec/spectec/clauses/S07.spectecdef @sec-iscallable "IsCallable" (kind ao params [arg : #"ECMAScript language value"] -> Boolean) vars [arg] {  if arg is not ty {Object} -> return false  if arg sat $HasMethod([[Call]]) -> return true  return false}

Every part of the clause is explicit and readable by name: @sec-iscallable identifies the clause (mapped to sorted ClauseId 1364 when emitting Lean), kind ao marks an abstract operation taking arg of sort #"ECMAScript language value" and returning Boolean, step 1 tests arg is not ty {Object}, and step 2 checks arg sat $HasMethod([[Call]]) before step 3 returns false. Running spectec-html renders those three steps back into spec.html's exact ecmarkup.

A step of the machine. Downstream, Lower compiles the body with its step numbers preserved. When EvaluateCall reaches IsCallable(func), the small-step machine pushes a frame for @sec-iscallable with arg bound to the callee; Ecma.Machine.step checks whether the callee is an Object in the store, inspects its [[Call]] internal method at step 2, and returns true or advances to step 3.

In the debugger. The example tests/run/iscallable.js calls both a function and an ordinary object: the debugger pauses at IsCallable step 2 for the function and step 3 for the object, displaying IsCallable above EvaluateCall in the spec stack alongside the value of arg.
